# Agent Note: Distributed admission keeps PostgreSQL authoritative

Status: implemented

English | [中文](2026-08-14-distributed-api-redis-worker.zh.md)

## Problem

The Harness Agent Loop, session store, and existing persistence implementations assume one process owns a live agent. Exposing that composition directly as a horizontally scaled API creates three coupled failures: an API process becomes both connection owner and executor, requests for one session can run concurrently on different replicas, and process loss can strand history or work without a durable command identity. Multi-tenancy adds a separate boundary: session ids alone cannot authorize reads or execution, and queue metadata cannot become the authority for tenant state.

## Decision

The distributed app separates stateless API admission from Worker execution. PostgreSQL owns tenants, owner-scoped sessions, command state, Harness session headers, and the append-only event log. Each command row is also the transactional outbox record. API replicas select undispatched rows with `FOR UPDATE SKIP LOCKED`, append them to one Redis consumer-group Stream, and then mark them dispatched; this deliberately permits duplicate delivery across a crash boundary.

Workers first acquire a renewable Redis lease keyed by tenant and session, then atomically transition one queued PostgreSQL command to running. The command status is the idempotency gate, while the lease makes a session a single-writer actor across processes. A Worker creates or resumes the ordinary Harness Agent under an internal `tenant/session` identity, runs the native loop and tools, uses the session-checkpoint policy before model requests and tool side effects, flushes the event log, and only then completes the command. The runtime is recreated for each command in this MVP, so PostgreSQL recovery rather than sticky routing owns continuity.

Redis is acceleration state only. Streams schedule admission, expiring keys carry leases and Worker heartbeats, and Pub/Sub wakes cancellation. PostgreSQL retains cancellation intent and serves event reads and SSE catch-up by monotonically contiguous sequence. Active-command heartbeats let an API pump return stale running commands to the outbox after two lease windows. An advisory lock serializes the idempotent schema migration when application replicas start together.

Tenant identity is carried into the internal Harness session id and every PostgreSQL primary or foreign key. API reads and writes include both tenant and owner where the surface is user-owned. Browser authentication uses scrypt password hashes, random opaque session tokens whose hashes are stored in PostgreSQL, and HttpOnly SameSite cookies shared by HTTP and WebSocket requests. Nginx clears caller-provided identity headers before proxying browser traffic. The API port and header-identity test/service seam stay private to the Compose network.

The browser tier is a separate Nginx container that serves a statically assembled `apps/web` shell and a dependency-closed client-plugin graph. A small authentication shell gates native Web startup, provides tenant registration/login/logout and an administrator model dialog, then loads the official conversation UI. Compose defines one scalable `api` service and one scalable `worker` service; container hostnames supply unique instance ids. Nginx re-resolves Compose DNS and load-balances ordinary RPCs and the two authenticated WebSocket downlinks across live API replicas while owning port 20810. Redis consumer-group membership distributes commands across live Worker replicas. API replicas implement the native browser contract over the same PostgreSQL commands and events used by `/v1`; the Web process therefore owns no session or Agent state.

Model configuration is tenant state in PostgreSQL. A tenant administrator selects Mock, DeepSeek, or OpenAI-compatible Chat Completions, a default model, an endpoint, and optionally a tenant key. API keys are sealed with AES-256-GCM under a deployment key and are never returned by the API. A Worker reads and decrypts the tenant snapshot for each command and never mutates a process-global API-key environment variable. DeepSeek constructs its operation-local direct adapter; OpenAI-compatible mode mounts the upstream pi-ai Cordis plugin with a read-only operation-local credential provider and a hand-declared `openai-completions` route. This prevents concurrent tenant work from crossing credential boundaries while retaining upstream stream and tool-call conversion.

The native composer and tool runtime share PostgreSQL-owned tenant Workspace records and session membership/order. Registration creates a default `/workspace` record, and the migration attaches every existing session to its tenant's default. Workspace RPCs and host-stream deltas implement the native client contract across replicas. One internal Workspace service exclusively mounts a persistent volume and maps the selected database identity to `/workspaces/<tenant-id>/<workspace-id>`; API and Worker replicas never mount that volume. A Worker obtains the upstream tool catalog and guidance when it builds a command runtime, registers model-visible proxy definitions, and forwards calls over an authenticated internal HTTP boundary. The Workspace service runs the original filesystem, ripgrep search, string editor, Bash, and background-job plugins in a long-lived Cordis context per workspace, so command execution and files remain shared when a later turn lands on another Worker.

Distributed integration preserves upstream plugin ownership. A Workspace runtime composition plugin mounts the original local providers and tool consumers as child Fibers, while a Worker-side Cordis adapter owns the remote catalog listener and proxy registrations. Their recursive disposal removes complete tool generations without custom cleanup. Agent-scoped upstream plugins remain in the Worker: `todo_write` records its snapshots in the PostgreSQL-backed session log, and the repeat-call reminder contributes its standard logged context after repeated identical calls. Plugins that require credentials, externally selected providers, or child-agent ownership remain absent until tenant-scoped configuration and the corresponding distributed lifecycle exist.

The internal service validates tenant and workspace UUIDs, derives storage paths rather than trusting the logical display path, rejects file/search/editor paths whose existing canonical ancestor escapes the selected root, forwards cancellation, and keeps port 3200 private behind a shared service token. This is deliberate logical routing, not a claim of hostile-code tenant isolation: one arbitrary Bash tool inside one container remains a shared trust boundary. Strong isolation requires changing the Workspace provider placement to a per-trust-domain container or microVM while retaining the Worker proxy contract.

## Alternatives considered

- **Keep agents inside API replicas and use sticky sessions**: rejected because API lifecycle and executor lifecycle stay coupled, failover depends on load-balancer affinity, and a lost replica still needs a durable recovery protocol.
- **Make Redis the command and transcript authority**: rejected because Stream retention, Pub/Sub loss, and Redis failover semantics are a poor ownership boundary for tenant records and append-only Harness history.
- **Add tenant and queue concepts inside Agent Loop**: rejected because they are deployment concerns; the native loop remains reusable and its model/tool/checkpoint behavior stays testable independently.
- **Hold a long-lived Session Actor on one Worker**: deferred because it reduces latency but requires actor placement, handoff, mailbox draining, and shutdown fencing. Per-command reconstruction proves the persistence and lease boundaries first.
- **Promise exactly-once queue delivery**: rejected because the outbox-to-Redis boundary cannot be atomic. At-least-once scheduling plus an atomic PostgreSQL command claim gives the required execution behavior without a distributed transaction.
- **Embed the Web UI in API replica one**: rejected because it makes one API a special ingress replica, bypasses API load balancing, and couples frontend rollout and health to admission capacity.
- **Mount the shared volume directly into every Worker**: rejected because model-controlled file and command side effects would occur in multiple executor containers, Worker replacement would also become storage attachment management, and the boundary would be harder to audit. One tool service owns all workspace I/O.
- **Create one Workspace container per tenant immediately**: deferred because it provides a stronger security boundary but requires placement, lifecycle, quota, cleanup, routing, and image orchestration that are outside this first shared-workspace phase. The internal proxy interface leaves that migration path open.
- **Implement another direct Chat Completions client in the distributed app**: rejected because the upstream pi-ai adapter already owns OpenAI-compatible streaming, tool calls, cancellation, usage, and error conversion. The distributed layer only supplies tenant-scoped configuration and credentials.

## Consequences

- Independently scaled API and Worker replica sets can process unrelated sessions concurrently, while one session remains serial and can resume through another API and another Worker.
- Native Harness context management, tool calls, checkpoint ordering, and event replay remain intact; Redis and tenancy do not enter model-visible context.
- The repository's native Web shell can create sessions, select the configured model route, submit and cancel prompts, recover history, and render live model and tool events through either API replica.
- Browser users can create isolated tenants and authenticate through a database-backed session; tenant administrators can change model configuration without rebuilding the containers.
- The same tenant model surface can route to an official OpenAI endpoint, an OpenAI-compatible gateway, or a keyless local Chat Completions server without introducing a second wire-protocol implementation.
- Every tenant has a selectable default Workspace, so the official composer can create a Workspace-bound session and start a conversation without bypassing the Web protocol.
- The Agent receives upstream `read`, `write`, `edit`, `glob`, `grep`, `str_replace_editor`, `bash`, `job_output`, `job_list`, and `job_kill` schemas and guidance, while all corresponding file and process work executes in the volume-owning Workspace container.
- The Agent also receives the upstream `todo_write` tool and repeat-call reminder in the Worker process; their session events use the same PostgreSQL persistence and cross-API replay path as the rest of the conversation.
- Workspace files survive Workspace-service and Worker restarts, and every Worker sees the same selected directory; background job registry state remains process-local to the Workspace service and does not survive its restart.
- File-oriented RPC calls have canonical-root checks, but arbitrary Bash execution makes the single-container topology one trust domain rather than a hard multi-tenant sandbox.
- PostgreSQL load and per-command runtime construction are higher than a sticky actor design, but recovery behavior is explicit and testable.
- A process crash can leave an old Redis pending entry; SQL recovery emits a fresh entry and the command gate prevents duplicate execution, but production operation still needs pending-entry reclamation, Stream trimming, dead-letter policy, metrics, and alerts.
- Password recovery, invitations and user lifecycle management, MFA/SSO, quota enforcement, audit logging, coarse stale timeouts, approval flows, distributed subagents, key rotation workflow, TLS ingress hardening, and PostgreSQL row-level security are not production-complete in this MVP.
